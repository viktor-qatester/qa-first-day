# Дорожная карта проекта «Первый день QA»

Статус: **собираем отзывы**.

Этот файл хранит направления развития, а не обязательства. Идея переходит в работу только после обсуждения, выбора приоритета и описания критериев приёмки.

## Текущий фокус

Не расширять приложение до получения обратной связи по первому законченному сценарию.

Главный ожидаемый отзыв — экспертная оценка работающего QA с большим опытом:

- насколько ситуации похожи на реальную работу;
- где процесс чрезмерно упрощён;
- чему новичка приложение может научить неправильно;
- какую одну рабочую ситуацию необходимо добавить;
- что стоит сохранить без изменений.

Дополнительно собрать отзывы начинающего тестировщика, человека без опыта и, по возможности, разработчика или тимлида.

## Как фиксировать отзыв

Для каждого наблюдения записывать:

1. Кто проверял и в какой роли.
2. Экран или место в сценарии.
3. Что человек ожидал.
4. Что произошло или показалось неправдоподобным.
5. Почему это важно.
6. Предложение, если оно есть.

Отзывы пока не превращать автоматически в разработку. Сначала объединить повторяющиеся замечания и выбрать одно небольшое улучшение.

## Возможные этапы

### 1. Проверка текущего прототипа — собираем отзывы

- Дать приложение 3–5 людям.
- Не объяснять прохождение заранее.
- Проверить понятность, реалистичность и учебную ценность.
- Отдельно получить экспертный отзыв опытного QA.
- Составить список подтверждённых проблем и предложений.

### 2. Углубление первого рабочего дня — на обсуждении

Возможные дополнения:

- мини-чек-лист перед тестированием;
- выбор тестового окружения;
- поиск противоречий в требованиях;
- Console вместе с Network;
- самостоятельный поиск бага на экране;
- сравнение API-ответов;
- простое составление SQL-запроса;
- определение Severity и Priority;
- улучшенное оформление баг-репорта;
- ретест исправления;
- короткий регресс перед релизом;
- итоговый разбор неправильных решений.

Предварительный приоритет — **ретест исправления и короткий регресс**, потому что сейчас сценарий почти не показывает работу QA после передачи дефекта разработчику.

### 3. Более заметные последствия решений — идея

- Слабый баг-репорт вызывает запрос дополнительной информации.
- Отсутствие доказательств задерживает исправление.
- Пропущенная проверка приводит к дефекту после релиза.
- Хорошая работа оставляет время на дополнительный регресс.
- Непрофессиональное общение вызывает разбор с наставником.

### 4. Улучшенный итог прохождения — идея

Показывать:

- сильные стороны;
- допущенные ошибки;
- пропущенные дефекты;
- качество баг-репорта;
- работу с требованиями;
- технические навыки;
- коммуникацию;
- рекомендацию для следующей тренировки.

### 5. Новые рабочие дни — отложено

Возвращаться к этому этапу только после проверки и углубления первого дня.

| День | Возможная тема |
|---|---|
| День 1 | Первый релиз интернет-магазина |
| День 2 | Регресс после срочного исправления |
| День 3 | Тестирование мобильного приложения |
| День 4 | API и интеграции |
| День 5 | Инцидент после релиза |
| День 6 | Собеседование Junior QA |

## Правило выбора следующего изменения

Следующая задача должна:

- подтверждаться обратной связью или явной учебной ценностью;
- улучшать один понятный участок сценария;
- иметь проверяемые критерии приёмки;
- не требовать одновременно переделывать всё приложение.

## Ближайшее решение

После получения отзывов сравнить их, выделить повторяющиеся замечания и выбрать **одно** улучшение первого дня. До этого новые дни и крупные функции не разрабатывать.
