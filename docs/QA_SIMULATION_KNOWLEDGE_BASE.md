# База знаний симулятора QA

Это рабочая опора проекта. Обновляем её после подтверждённого экспертного отзыва или изменения сценария.

## Методические правила

1. Сначала определить источник истины: требования, конфигурация, Swagger/OpenAPI, схема данных.
2. DevTools и перехват запросов подготовить до воспроизведения действия.
3. Разделять наблюдения по слоям: интерфейс, Network, API, база данных.
4. Не делать вывод о данных БД только по числу запросов API.
5. Разделять транспортный HTTP-статус и бизнес-результат в теле ответа.
6. Использовать точные термины: два разных идентификатора — это два объекта; дубликат требует совпадения данных по определённому критерию.
7. В SQL перечислять нужные поля, ограничивать объём и задавать сортировку. В задаче с таблицей `orders` используется MS SQL Server и учебные поля `id`, `user_id`, `total`, `status`, `order_date`. Проверка должна оценивать смысл ограниченного запроса, а не совпадение с одной строкой: допустимы другой регистр, переносы, перестановка выбранных полей и лимит от 2 до 10 строк. Для сравнения двух заказов нужны `id`, `user_id`, `order_date`, фильтр `user_id = 77` и сортировка `order_date DESC`; запрещены `SELECT *`, лишние команды и неограниченная выборка.
8. При расхождении воспроизведения сравнивать шаги, окружение, данные, сборку и время действия.
9. После исправления проводить ретест исходного дефекта и короткий регресс соседнего риска.
10. До выбора все карточки должны быть нейтральными; правильность показывается только после действия пользователя.
11. Если браузер запрещает localStorage, учебная смена может продолжиться в текущей вкладке, но интерфейс обязан предупредить, что после закрытия вкладки прогресс не сохранится.

## Каркас учебной задачи

- Контекст и скоуп сборки.
- Источник истины и чек-лист.
- Пользовательское воспроизведение.
- Подготовка инструментов.
- Сбор доказательств по слоям.
- Безопасная проверка данных.
- Сверка контракта.
- Точный баг-репорт и коммуникация.
- Ретест, регресс и рекомендация по релизу.

## Правило выпуска

Изменение проходит: критерии приёмки → реализация → smoke → полный E2E → проверка мобильного интерфейса → коммит и push → публикация в нужный Site → проверка опубликованной версии.
- Публичный и тестовый Sites — отдельные проекты. Коммит или push в GitHub сам по себе не обновляет Site; публиковать нужно в явно выбранный Sites-проект.
- Один адаптивный сайт открывается и на телефоне, и на компьютере. Автотест на мобильной ширине не заменяет проверку в реальном мобильном браузере; указывать поддержку iOS как проверенную можно только после проверки на устройстве или эмуляторе.

## Развитие рабочего стола

- Рабочий стол становится следующим интерфейсом того же Дня 1, а не отдельным несвязанным демо.
- Переносить сценарий частями: начать с задачи, требований, короткого чек-листа и исследования промокода; дальше продолжать на уже существующие этапы DevTools, SQL, API и оформления дефекта.
- При переходе из рабочего стола сохранять имя, принятые решения и баллы в существующем локальном прогрессе, чтобы пользователь не проходил один и тот же этап повторно.
- После проверки корзины передавать пользователя на этап подготовки исследования: DevTools/Network должны быть открыты до повторного воспроизведения заказа; этот этап нельзя пропускать при передаче между интерфейсами.
- Сохранять промежуточный прогресс рабочего стола отдельно; при передаче в карточный маршрут включать значения в его существующую схему и не начислять одни и те же баллы второй раз.
- Если в браузере уже есть другое сохранённое прохождение, архивировать его перед переходом на новый маршрут.
- Интерактивные учебные инструменты явно обозначать как симуляции и объяснять, какие реальные выводы подтверждает каждый артефакт.
